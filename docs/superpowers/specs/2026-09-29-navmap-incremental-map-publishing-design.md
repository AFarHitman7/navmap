# Incremental map publishing and multi-indoor navigation design

**Status:** Approved in conversation on 2026-09-29; written spec awaiting review. Supersedes conflicting prototype limits in `2026-09-27-navmap-prototype-design.md` and `navmap-backend/CONTRACT.md` for future schema-v2 publications. Existing v1 publications remain immutable.

## Goal and scope

Let an organizer publish a useful outdoor map as soon as its boundary exists, then incrementally add destinations, multiple entrance-linked indoor plans, routes, barriers, background images, and Android Wi-Fi surveys. Update web, backend, and Android together; a web-only editor change cannot make these snapshots usable on Android. Retain the single-venue, local-disk, offline-capable prototype architecture and its existing authentication, versioning, checksums, and upload limits. No manual AP entry on web. No indoor width or area field is required to create or first publish a map.

## Current behavior and publish investigation

`navmap-web/src/Organizer.tsx` saves before posting to `/api/admin/publish`; API and save errors appear in the workspace status. `navmap-backend/src/draft.ts` currently requires one indoor zone, positive indoor width, one outdoor entrance with a cross-zone edge, all nodes connected, and an indoor anchor. `src/publish.ts` additionally requires 3–4 registered APs and three scans with two common APs for each indoor place. `navmap-web/src/editor/model.ts` repeats much of this in its checklist, and the mobile v1 validator also requires exactly two zones and 3–4 APs. These are demonstrable reasons a newly drawn map cannot publish; they do **not** prove the cause of every reported failed attempt. Before modifying publish logic, reproduce save → publish on an outdoor-only draft and on the existing fixture, record response status/body and whether failure occurred during save or publish, then add regression tests for the confirmed failure paths. Keep the server as the authority for publish validation; show individual failures next to relevant steps rather than only a concatenated status message.

## Versioned data contract and migration

Use `schemaVersion: 2` for new publications; update backend, web, and Android validators and fixtures in lockstep. Do not mutate v1 manifest JSON, asset paths, or existing local packs. Both clients accept v1 manifests and their v1 graph behavior, and v2 manifests with the new behavior. Android's active-pack swap remains atomic: an incompatible/partial v2 download preserves its current pack. Existing editable v1 draft data is read and migrated to v2 draft shape on load/save without deleting images or samples: its north-up outdoor rectangle becomes a zero-rotation footprint and its one indoor zone retains its image, nodes, and portal edge. Require an explicit compatibility test for old drafts, old published manifests, and old saved Android packs. Do not publish v2 until the mobile client release supports v2; otherwise keep the last v1 version usable and show a clear update-needed message to outdated clients.

The v2 draft/snapshot has one outdoor zone and zero or more indoor zones. Each zone has a stable ID, `kind`, `navigationMode: 'free' | 'paths'`, and `barriers` as line segments of normalized endpoint coordinates `[0,1]`. The outdoor zone has a rotated geographic footprint and a derived axis-aligned geographic envelope for map fitting and coarse GPS inclusion. Each indoor zone has a rotated geographic footprint, `entranceNodeId` referencing an outdoor node, and `entryNodeId` referencing its own indoor node. A single explicit portal edge joins that pair. Remove the single global `entranceNodeId` in v2; older clients continue to use it only for v1. Explicit ordinary edges remain `{from,to,meters}` and belong to a single zone; portal edges have their own explicit cross-zone role so arbitrary cross-building edges are invalid. Places, anchors, APs, and profiles can be empty; reference checks reject dangling IDs and wrong zone assignments. Every published place must be reachable from another routable node in its zone or its portal network when there is more than one route node; do not require any node, place, anchor, indoor zone, image upload, AP, or survey for an outdoor-boundary-only publication. Preserve per-version immutable image refs and digests, including transparent fallback images for zones without a saved background.

The footprint is represented by a center latitude/longitude, positive `widthMeters` and `heightMeters`, and clockwise `rotationDegrees` relative to north, normalized to `[0,360)`. This is geometry derived from a geographic drawing, not a required width/area form. Store area as a computed display value in square metres, not as independent editable state. Existing outdoor `bounds` remains a derived envelope, never a second source of truth. Convert points via a local metre-scale geographic projection around the center; use the same forward/inverse transform for polygon display, map clicks, GPS matching, node reprojection, rotation, crop, and visitor display. Document projection accuracy limits for venue-sized footprints and reject invalid/oversized or pole-crossing geometry. Uploading an indoor image does not change its footprint or node coordinates; fit/crop it with a visible preview rather than stretching the authored geometry silently. An optional later measured-width override must be explicit and must not silently disagree with the map footprint.

## Organizer workflow

The outdoor boundary can be drawn and rotated on the interactive OSM map. Save and publish are available immediately after a valid boundary. On an outdoor node, “Create indoor plan” opens a footprint drawing/rotation tool on the outdoor map and creates one new indoor zone with a stable unique ID plus an indoor entry node and portal; multiple outdoor nodes may have plans, and plans are selected by entrance/building label rather than a single Indoor toggle. One entrance owns one plan in this release; multiple doors to the same indoor zone and multiple floors are deferred. Prevent accidental portal deletion/orphaning: deleting an entrance or its plan asks for confirmation and removes or relinks dependent geometry deliberately. Rotating/resizing a footprint preserves indoor normalized nodes and updates its derived scale; resizing/redrawing the outdoor footprint preserves outdoor nodes' geographic positions or warns before they would leave the boundary. Undo/save/reload preserve these relationships. The visitor UI offers an outdoor view plus a labelled indoor-plan picker and switches to the next zone when a route traverses a portal. An outdoor-only publication shows the map with an honest “add destinations to enable routes” state, not broken route controls.

## Routing semantics

Free mode is the default *per zone*: each pair of distinct nodes in that zone is an implicit, undirected, straight-line candidate, weighted by geographic metres for outdoor nodes and footprint-derived metres for indoor nodes. A candidate crossing a barrier line is excluded, including collinear overlap; touching only at a shared endpoint is allowed. Barriers are normalized line segments authored on the zone surface, visually inspectable and removable; use a documented geometric tolerance and robust segment-intersection tests. Do not draw all implicit edges in the editor; display a selected route, barriers, portal markers, and an explanation of the active mode. In path-only mode, only authored intra-zone edges are used, weighted by their stored positive metre lengths. Switching to path-only must surface newly unreachable places before publish; a barrier does not silently invalidate a hand-authored explicit route, and the UI explains that explicit paths govern this mode. Portal edges alone cross zones and have an explicit positive traversal cost. Graph construction and deterministic Dijkstra/path-length logic must match in web and Android; server publish validation must use the same semantics, verified against shared fixture cases. Tests include free-zone direct routes, a blocked crossing with an alternate node, no alternate route, explicit-path mode, multi-indoor portal routing, and no unintended cross-zone shortcut. Do not interpret barriers as full floor-plan wall extraction.

## Map backgrounds and tile licensing

Keep `tile.openstreetmap.org` strictly for interactive online views with visible attribution, normal browser cache/Referer behavior, and no bulk/offline capture. Its tile usage policy explicitly prohibits offline tile packages and prefetch; do not implement a screenshot/stitched tile export from this source. In web editing, a footprint can *preview* the live OSM content beneath it as an online-only visual placeholder. “Use map as background” is an opt-in operation available only when an administrator has configured a source that **explicitly permits saved static images and offline redistribution**, with its attribution/license recorded. A small backend snapshot-source interface takes a footprint, output pixel dimensions and rotation and returns a size-bounded PNG/JPEG/WebP plus attribution; it fetches only the organizer-requested region, never a zoom pyramid. The backend validates returned bytes, content type, and size (existing 1.5 MB cap), stores the image like an upload, and publishes a digested immutable asset. The preview and captured image must use the same extent/rotation; show a before-save preview and retain source attribution in both web and offline Android. A provider that cannot render rotated regions may supply an axis-aligned crop that is rotated/cropped locally without extra tile requests. If no licensed source is configured, it fails, or its output exceeds limits, show a specific message and let the organizer upload their own image or publish a blank background. No undisclosed third-party endpoint or assumed offline license. Continue to show imagery-source attribution independently of OSM interactive-layer attribution.

## Survey workflow and publication

Remove the web AP-entry form and AP count/survey checklist gates. Android survey mode is organizer-authenticated, operates after the first publication, lists discovered BSSIDs from fresh device scans, lets the surveyor choose stable permitted APs, and submits the chosen allowlist to the existing authenticated AP endpoint before uploading samples. Scan input validation and timestamp deduplication remain server-side. Do not automatically trust every neighboring access point or expose BSSIDs in public UI other than the existing snapshot data needed by the matcher. Publishing includes only viable profiles assembled from surveyed places and selected APs; incomplete surveys produce no usable Wi-Fi fix, not a publish rejection. Android's matcher checks profile sufficiency/freshness and falls back to GPS outdoors, QR, or manual selection. Later publish versions incorporate surveys; the first outdoor-only snapshot has `aps: []` and `profiles: []` and remains fully usable for offline map viewing. Mobile survey screens must let the surveyor choose an actual indoor place rather than assuming `room-a` exists.

## Delivery and verification boundaries

This is a cross-repo release roadmap, not one giant implementation batch:

1. **Publish baseline and v2 compatibility:** reproduce existing failure; allow boundary-only v2 snapshots; update web/backend/mobile validators and fixture, Android pack compatibility, and empty visitor states. This is independently publishable once clients are coordinated.
2. **Multi-indoor and rotated footprints:** create, edit, save and display multiple entrance-linked plans; derive dimensions; update visitor/Android zone selection and geometry rendering. No implicit route changes yet.
3. **Routing modes and barriers:** implement shared semantics, mode controls, validation and route visualization across clients; preserve v1 behavior.
4. **Licensed static map background:** online-only preview, opt-in capture interface, attribution, offline asset and failure handling. Upload/blank remain fallback.
5. **Mobile-led Wi-Fi surveying:** AP discovery/selection, authenticated registration, surveyed profiles, positioning fallback; verify on a real Android device.

Use focused unit tests in each repository, backend publish/immutability/image tests, web editor component tests and Playwright author→publish→visitor routes, and Android pack/route/survey tests. Manually exercise: no-image boundary-only publish; re-publish after indoor addition; two distinct entrances; rotated rectangle/cropped image; blocked free-mode route and path-only route; Android download/offline display and old-pack rollback; missing snapshot provider; partial survey; expired auth/save failure with draft retained. Continue respecting the existing tile policy, immutable asset digests, HTTPS/LAN constraints, and upload limit.

## Out of scope

No multi-floor indoor stacks, polygon interiors, corridor extraction from imagery, turn-by-turn obstacle avoidance beyond authored barriers/paths, bulk OSM tile downloading, automatic adoption of all scanned APs, or new SaaS infrastructure. Keep the existing v1 fixtures and users' uncommitted work intact.
